# 项目升级可行性评估

## 📊 现状分析

### 硬件配置
- **MCU**: STM32F429IGT6 (Cortex-M4)
- **主频**: 180MHz
- **RAM**: 192KB (0x20000000 - 0x30000) + 64KB (0x10000000 - 0x10000)
- **Flash**: 1MB (0x08000000 - 0x08100000)
- **WiFi**: ATK-MW8266D (ESP8266)
- **当前功能**: MQTT 数据上报、心跳保活、自动重连、多任务管理

### 当前瓶颈
```
剩余 Flash: 1MB - 49224B(代码) - 18940B(常量) ≈ 931KB
剩余 RAM:   ~120KB（FreeRTOS + 各任务堆栈）
外设:       SDRAM(4MB), 未利用
存储:       未有 SD 卡或 Flash 模块
```

## ✅ 2.2 本地存储与断点续传（推荐实现）

### 可行性评估

| 条件 | 评分 | 备注 |
|------|------|------|
| **Flash 空间** | ⭐⭐⭐⭐⭐ | 931KB 空余足够 FatFs + 数据缓存 |
| **RAM 空间** | ⭐⭐⭐⭐ | 可通过缓冲区设计优化 |
| **难度** | ⭐⭐⭐ | 中等（FatFs 移植有现成方案） |
| **时间成本** | ⭐⭐⭐ | 1-2 周（含调试） |
| **收益** | ⭐⭐⭐⭐⭐ | **极高**（核心卖点） |

### 🎯 实现方案（推荐）

```
选择 1：SPI Flash（推荐 ⭐⭐⭐⭐⭐）
  优点：
    ✅ 成本低（10 元以内）
    ✅ 不需要额外 IO（利用已有 SPI）
    ✅ 容量足够（16MB 或 32MB）
    ✅ 集成度高
  
  缺点：
    ❌ 需要驱动移植（但网上资源多）
  
  容量规划：
    - 总容量：16MB
    - FatFs 文件系统：1MB
    - 数据存储：15MB
    - 预期容量：采集 1 分钟一次，1 年数据 ≈ 500KB（足够）

选择 2：SDRAM 作缓冲（备选）
  优点：
    ✅ 速度快（4MB 足够缓存）
    ✅ 无驱动（已有）
  
  缺点：
    ❌ 掉电丢失（需要配合备用电池）
    ❌ 容量有限
  
  适用场景：短期缓冲（几小时数据）

选择 3：SD 卡（不推荐）
  原因：
    ❌ 协议复杂（SDIO）
    ❌ 占用 IO 资源
    ❌ 可靠性风险（接触不良）
```

### 📋 详细实现步骤

#### 步骤 1：添加 SPI Flash 驱动

```c
// 伪代码框架
#define FLASH_SECTOR_SIZE   4096      // 4KB 一个扇区
#define FLASH_TOTAL_SIZE    (16*1024*1024)  // 16MB
#define DATA_STORAGE_START  0x100000  // 1MB 后开始存储

// 关键函数
void flash_init(void);                    // 初始化
void flash_write(uint32_t addr, uint8_t *data, uint32_t len);
void flash_read(uint32_t addr, uint8_t *data, uint32_t len);
void flash_erase_sector(uint32_t addr);
```

#### 步骤 2：集成 FatFs 文件系统

```c
// 配置 FatFs
// ff_conf.h
#define FF_USE_MKFS     1   // 支持格式化
#define FF_USE_STRFUNC  1   // 支持字符串操作
#define FF_CODE_PAGE    437 // 代码页

FATFS fs;
FIL file;
DIR dir;
FILINFO finfo;

// 初始化
f_mount(&fs, "0:", 1);
```

#### 步骤 3：数据缓存策略

```c
// 缓存结构体
typedef struct {
    uint16_t timestamp;        // 时间戳
    uint16_t ap3216c_als;      // ALS 数据
    uint16_t ap3216c_ir;       // IR 数据
    uint16_t ap3216c_ps;       // PS 数据
    uint8_t  dht11_temp;       // 温度
    uint8_t  dht11_humi;       // 湿度
} SensorData_t;

// 循环缓冲区
#define BUFFER_SIZE 100  // 缓存 100 条数据（约 100 * 8 = 800 字节）
SensorData_t sensor_buffer[BUFFER_SIZE];
uint16_t buffer_head = 0, buffer_tail = 0;

// 策略：
// 1. 采集数据 → 写入环形缓冲区（RAM）
// 2. 缓冲区满或 5 分钟一次 → 写入 Flash 文件
// 3. 网络连接 → 读取 Flash，逐条上传
// 4. 上传成功 → 删除 Flash 中的文件
```

#### 步骤 4：网络恢复后的上传

```c
void upload_historical_data(void)
{
    FIL file;
    SensorData_t data;
    UINT bytes_read;
    
    // 打开历史数据文件
    if (f_open(&file, "data.csv", FA_READ) == FR_OK)
    {
        while (f_read(&file, &data, sizeof(data), &bytes_read) == FR_OK && bytes_read > 0)
        {
            // 逐条上传
            send_mqtt_publish(data);
            
            // 模拟网络波动处理
            if (network_error)
            {
                f_close(&file);
                return;  // 网络又断了，下次继续
            }
        }
        
        // 全部上传成功
        f_close(&file);
        f_unlink("data.csv");  // 删除已上传的数据
    }
}
```

## ⚠️ 2.3 设备影子与双向控制（需谨慎）

### 可行性评估

| 条件 | 评分 | 备注 |
|------|------|------|
| **Flash 空间** | ⭐⭐⭐ | 足够但紧张 |
| **RAM 空间** | ⭐⭐ | 问题点！|
| **难度** | ⭐⭐⭐⭐ | 较难（JSON 深度解析） |
| **时间成本** | ⭐⭐⭐⭐ | 2-3 周 |
| **收益** | ⭐⭐⭐ | 中等 |

### 🚨 关键问题

#### 问题 1：JSON 解析占用 RAM

```c
// 你现在用的 cJSON（简化版）
cJSON *root = cJSON_CreateObject();
cJSON_AddNumberToObject(root, "als", 1024);
// 这只是简单的序列化

// 但设备影子需要深度解析
{
    "state": {
        "desired": {
            "sample_interval": 60,
            "alarm_threshold": 100,
            "lcd_brightness": 200
        },
        "reported": {
            "status": "online",
            "version": "1.0"
        }
    }
}

// 解析这种嵌套结构很耗 RAM
// 估计需要额外 20-30KB RAM（你没有这么多）
```

#### 问题 2：EEPROM 读写寿命

```c
// STM32F429 内部 Flash 作 EEPROM
// 寿命：100,000 次擦写

// 如果每 1 小时更新一次配置
// 100,000 / (24 * 365) = 11.4 年（可以）

// 但如果频繁更新（每分钟）
// 寿命：100,000 / (24 * 60 * 365) = 0.096 年 = 35 天（寿命短！）
```

### 🎯 是否值得实现？

```
适合实现的场景：
  ✅ 设备需要远程配置（采样频率等）
  ✅ 配置不频繁变更（一天几次以内）
  ✅ 用户有足够的 RAM（> 150KB）
  
不适合实现的场景：
  ❌ 配置频繁变更（秒级更新）
  ❌ RAM 严重不足（现状）
  ❌ 设备影子完全同步（过于复杂）
```

## 💡 综合建议

### 📌 优先级排序

```
1️⃣ 必做：2.2 本地存储与断点续传
   理由：
   ✅ 成本低（10 元 SPI Flash）
   ✅ 技术难度适中（1-2 周）
   ✅ 收益极高（核心功能）
   ✅ RAM 占用少（2KB）
   
   实现建议：
   - 先做 SPI Flash 驱动
   - 然后集成 FatFs
   - 最后做数据缓存和上传逻辑
   
   预期效果：
   - 网络不稳定时数据不丢失
   - 可上报历史 1 个月数据
   - 可做成卖点（断点续传）

2️⃣ 可选：2.3 简化版设备影子
   理由：
   ✅ 功能完整性加分
   ⚠️ 但要简化实现
   
   简化方案：
   - 不用完整 JSON 解析器
   - 只支持 3-5 个关键配置项
   - 用简单 KV 对存储（不用嵌套结构）
   - 配置保存到 EEPROM，但设计防抖机制
   
   示例：
   {
       "interval": 60,      // 采样间隔（秒）
       "alarm_temp": 35,    // 报警温度
       "lcd_on": 1          // LCD 开关
   }
   
   预期工作量：3-4 周
   预期 RAM：额外 5KB
```
