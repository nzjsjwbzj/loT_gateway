# 简历项目真实性学习计划（AI 代码项目）

## 目标
- 在不“假装会”的前提下，把当前 AI 生成代码转化为你能独立讲清、改动、排障的真实能力。
- 让简历表述与实际掌握程度一致，面试时可证明“我会维护与演进这套代码”。

## 总体策略
- 不建议整份代码“照抄重写一遍”作为唯一学习方式。
- 建议采用“可验证学习闭环”：理解 -> 复现 -> 小改 -> 排障 -> 讲解。
- 简历用语强调“AI 辅助开发 + 我主导集成、调试、验证”，避免“独立从零开发”的不实表述。

## 分阶段实施步骤

### 第 1 阶段：建立可讲清的系统图
1. 画出任务与数据流：
   - `ap3216c_task` 采集
   - `net_task` 连接/缓存/补发
   - SPI Flash 缓存区结构与状态位（FF/A5/00）
2. 写一页“关键状态机”：
   - 在线发送
   - 断网缓存
   - 重连补发
3. 对每个状态写触发条件与退出条件。

### 第 2 阶段：最小复现（不看代码复述）
1. 不打开源码，口述以下函数职责：
   - `flash_store_push`
   - `flash_store_peek`
   - `flash_store_mark_sent`
   - MQTT 重连/退避逻辑
2. 用白板写出记录格式：
   - `flag(1) + len(2) + payload(253)`
3. 解释为什么会出现“pending 不变 / sent_total 为 0”的典型故障。

### 第 3 阶段：做 3 个小改动（证明可维护）
1. 把补发策略改为“每轮补发 3 条”并验证。
2. 给缓存模块增加“启动时是否清空历史”的开关宏。
3. 给看门狗加缺失任务位掩码打印（仅调试开关下）。

### 第 4 阶段：做 2 个故障闭环（证明可排障）
1. 故障 A：断网 60 秒后恢复，验证 pending 下降与 sent_total 增长。
2. 故障 B：MQTT Broker 关闭重开，验证重连与历史补发。
3. 每个故障输出“现象-定位-修复-验证”四段记录。

### 第 5 阶段：简历与面试表述收敛
1. 简历改成事实描述：
   - “基于 AI 辅助完成代码骨架，我负责 FreeRTOS 集成、SPI Flash 缓存、重连补发调试与验证。”
2. 准备 3 个可追问点（每个 1 分钟）：
   - 为什么 `flag=0x00` 要作为可复用槽位
   - 为什么软件看门狗阈值要小于 IWDG 超时
   - 为什么离线缓存要在生产侧兜底而不只在 net_task

## 验收标准（达到才写入简历“熟练”）
- 能独立解释核心模块，不依赖看源码。
- 能在 30 分钟内完成一个小需求改动并跑通验证。
- 能独立定位一次缓存/重连异常并给出修复。

## 风险与规避
- 风险：只会“看懂”，不会“改动”。
  - 规避：每阶段必须有代码改动与验证记录。
- 风险：简历表述过度。
  - 规避：只写你能现场画图讲清并现场改动的部分。

## 建议结论
- 不用整份重写或照抄。
- 你需要的是“带验证的可维护能力”，这比“重写一遍”更接近真实工程与面试标准。
